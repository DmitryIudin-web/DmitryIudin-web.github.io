# Перенос существующего бота с Windows на действующий VPS

Этот порядок предназначен для сервера, на котором уже работают приложения.
`bootstrap-vps.sh` готовит новый сервер; его нельзя запускать здесь без проверки
всех действий с пакетами, SSH, firewall и сервисами. Адрес и перенос выбирает владелец.

После переключения Telegram обслуживает VPS. Компьютер можно выключать;
файлы, программы и браузер этого компьютера сами по себе на сервере не появляются.

## Подготовка без остановки бота

1. Проверить CPU, доступную память, диск, работающие сервисы, опубликованные порты
   Docker и действующий SSH-доступ. Записать контрольные HTTP/HTTPS-ответы приложений.
   Устранить причину перегрузки до добавления нового процесса.
2. Сохранить изменяемые настройки сервера в приватной резервной копии. При изменении
   SSH/firewall иметь проверенный ключ, отдельное соединение для проверки и
   ограниченный по времени откат. Отменить откат только после отдельного чтения
   фактических настроек и проверки доступа извне.
3. Создать отдельного пользователя `hermes` без `sudo`, `docker` и других
   административных групп. Приватный профиль хранить вне рабочей копии сайта.
   Использовать каталог 700 и файлы с ключами, памятью и историей 600.
4. Установить проверенный runtime 0.21.1 и Python 3.11. Для Telegram и локального
   голоса достаточно core и extras `messaging`, `voice`, `edge-tts`; браузеры,
   desktop и локальная языковая модель для этого не требуются. Зависимости ставить
   по зафиксированному `uv.lock`, не обновляя сторонние приложения VPS.
5. Для входящего русского голоса подготовить `faster-whisper`, модель `base` и
   `stt.local.language: ru`. Для преобразования исходящего аудио нужен `ffmpeg`.
   Выделить место и для модели, и для журналов после установки.
6. Подготовить рабочую копию нужной ветки сайта и проверить fingerprints runtime,
   затем выполнить `verify-runtime.py`. Не переносить GitHub-ключ публикации или
   административный SSH-ключ в профиль бота.

Если требуется перезагрузка самого VPS, сначала проверить установленные ядра,
загрузочную конфигурацию, отсутствие работающего обновления пакетов и автозапуск
всех приложений. После загрузки проверить SSH, firewall, контейнеры и реальные
HTTP/HTTPS-ответы. Состояние `enabled` само по себе не доказывает успешный старт.

## Снимок и переключение

1. Отключить прежний автозапуск Windows, сохранив его настройки для отката.
   Если изменение Scheduled Task недоступно, можно сохранить и заменить на
   завершающийся без запуска файл, который уже вызывает эта задача, при наличии
   права владельца на этот файл. Это не меняет защищённое определение задачи.
2. Штатно остановить Windows gateway и проверить отсутствие его процессов,
   включая дочерний процесс Python. Только затем делать снимок.
3. Перенести `.env`, `auth.json`, `config.yaml`, `SOUL.md`, нужные навыки, память,
   сессии, задания и базы. Для SQLite использовать backup API и `quick_check`,
   сверить количество записей. Копирование одного `state.db` без учёта WAL
   может потерять последние сообщения.
4. Передавать приватные данные по SSH. Не сохранять их в публичной рабочей копии,
   командной строке или отчёте. Сверить контрольные суммы принятого снимка.
   При обрыве сначала проверить, что уже записано на сервере, и только затем
   выбирать повтор или восстановление.
5. Не переносить Windows runtime, исполняемые файлы, launcher, PID/lock-файлы,
   heartbeat, временные каталоги и старые логи как действующее состояние Linux.
   Пути Windows в пользовательских заданиях и интеграциях проверить отдельно.
6. Установить Linux-путь `terminal.cwd`. Применить `profile.py apply --mode existing`
   и выполнить отдельный `profile.py check` с путём runtime. Это обновит управляемые
   ссылки на рабочую копию и сохранит существующие настройки интеграций.
7. Установить службу от имени `hermes`, сначала без запуска:

   ```bash
   # Выполняется администратором; значения ниже — пример размещения.
   HOME=/home/hermes HERMES_HOME=/home/hermes/.hermes \
     /home/hermes/.hermes/hermes-agent/venv/bin/python -m hermes_cli.main \
     gateway install --system --run-as-user hermes --no-start-now --start-on-login
   ```

8. Проверить unit и права владельца созданных файлов. Настроить ограничения,
   затем запустить службу. Один Telegram-токен должен обслуживать один gateway;
   прежний Windows-процесс к этому моменту уже остановлен.

## Ограничения на общем сервере

Пределы подбираются по измерениям при голосовом запросе. Для небольшого сервера
возможная начальная настройка — одна активная сессия, CPUQuota 75%, MemoryHigh
768M, MemoryMax 1024M и MemorySwapMax 256M. Это не гарантия достаточной памяти
для других моделей и длинных параллельных задач. Проверять OOM, перезапуски,
задержку ответа и запас ресурсов остальных приложений.

Ограничения оформлять отдельным systemd drop-in, чтобы обновление основного unit
их не удалило. `User=hermes`, `NoNewPrivileges=true`, пустой `CapabilityBoundingSet`,
`ProtectSystem=strict` и разрешённая запись только в домашний каталог ограничивают
права процесса. Закрыть для службы каталоги сторонних приложений и их данных,
административные ключи и Docker socket. Проверить доступ из пространства файловой
системы работающей службы, а не только прочитать текст конфигурации.

SSH проверять новым соединением с ключом и отдельной неуспешной попыткой без ключа.
У Telegram сохранить список разрешённых пользователей. Для long polling открывать
дополнительный входящий порт бота не требуется. Настройки бота не заменяют firewall.

У Docker учитывать публикацию портов через DNAT и внутренние маршруты reverse
proxy. Для контейнерных JSON-журналов использовать штатные `max-size`/`max-file`,
а не внешний `copytruncate`: вмешательство в эти файлы может нарушить работу
Docker. Новые настройки логирования не применяются к старым контейнерам сами;
пересоздание требует сохранения образа, переменных, портов, сетей и **всех** томов,
включая анонимные. Не применять общий `prune` для такой миграции.

## Приёмка и откат

- Проверить источник кода, владельца процесса, автозапуск, состояние Telegram,
  отсутствие конфликтов polling, ошибок доступа, OOM и повторных рестартов.
- Проверить целостность баз, модель и fallback, ограничения пользователей и
  реальные запреты terminal handler. Эти запреты не являются полной изоляцией кода.
- Владелец отправляет обычное сообщение и голосовое на русском и подтверждает
  правильный ответ. `connected`, запись ответа в SQLite или успешный HTTP-код
  не доказывают доставку владельцу и правильность распознавания его голоса.
- Снова проверить приложения, firewall, CPU, доступную память и свободный диск.

Для отката сначала остановить VPS gateway и проверить отсутствие его процесса.
Если после переключения появились новые сообщения, сохранить актуальные базы
и подготовить обратный перенос состояния: старый снимок Windows этих сообщений
не содержит. Затем вернуть прежний Windows launcher и запустить одну локальную
копию. Не включать её одновременно с серверной.

Записать результаты, время переключения и пути приватных резервных копий
в непубликуемом отчёте. Этот документ не должен содержать реальные адреса,
идентификаторы пользователей, ключи, переписку или копии конфигураций.
