# Контур измерения Яндекс.Директа — что сделано кодом (03.09.2026)

Источники требований:

- `growth/yandex-direct/2026-05-14-direct-bounce-audit.md` — аудит отказов
  кампании `709743299` / группы `5749089993`; осторожный вариант применён
  14.05.2026 (у объявлений заменены только URL и UTM).
- `plans/2026-09-02-ast-reserve-v2.md` — план AST Reserve v2 (п. 4.2 «Право и
  данные», п. 5 «Гигиена»).

Оба документа лежат вне этого репозитория. Здесь реализована только та их
часть, которая исполняется кодом статического сайта avtonds.ru.

## Зачем

Аудит заканчивается шагом 5: «через 48–72 часа проверить отказы по
`utm_content` и `utm_source_type`». Проверить их было нечем.

После правок 14.05.2026 объявления ведут на URL с одиннадцатью параметрами
(пять UTM плюс шесть шаблонов Директа: `utm_campaign_id`, `utm_group_id`,
`utm_source_type`, `utm_position_type`, `utm_device`, `utm_retargeting`).
Рантайм `assets/ast-conversion.js` сохранял только пять стандартных UTM.
Шесть параметров Директа терялись на входе, а Метрика не считает их UTM и
никуда не выводит сама.

Практическое следствие: `utm_source_type` — единственное измерение, которое
отделяет автотаргетинг от поиска, а именно автотаргетинг дал 529 из 530
показов и 65,45 % отказов. Без него главный вывод аудита нельзя было ни
подтвердить, ни опровергнуть.

Отказ — метрика уровня визита, поэтому параметры цели (`reachGoal`) его не
сегментируют. Нужны параметры визита (`ym(id, 'params', …)`).

## Что сделано кодом

Изменён один файл — `assets/ast-conversion.js`.

| Что | Как реализовано |
|---|---|
| Полный набор параметров источника | `SOURCE_KEYS` = 5 UTM + 6 шаблонов Директа. `persistUtm()` сохраняет их в `sessionStorage` по первому касанию (прежняя логика «первое касание выигрывает» не изменилась). |
| Параметры визита в Метрику | `sendVisitParams()` отправляет `ym(106049767, 'params', { ast_source: {…} })` с параметрами источника и `landing_page`. Ретраи каждые 1,5 с (до 20 попыток) — Метрика на сайте грузится с задержкой, схема та же, что у `getClientID` в A6. Дублируется в `window.dataLayer` событием `ast_source_params`. |
| Тишина на органике | Если в URL нет ни одного параметра источника, `ast_source` не отправляется — иначе отчёт был бы зашумлён прямыми заходами и органикой. |
| Источник в CRM | Скрытые поля форм заполняются всеми одиннадцатью параметрами, а не пятью. Заявка из Директа теперь несёт объявление, группу и тип трафика. |
| Цель `ast_form_start` | Аудит: «считать не CTR, а qualified lead / form start / messenger click». Событие шлётся при первом фокусе в поле лид-формы или при открытии квиза, один раз на визит (дедупликация как у `ast_contact`). |
| Версия согласия на ПДн | План, п. 4.2: версия текста фиксируется вместе с заявкой. Рантайм **читает** `consent_version` со страницы и переносит его в формы, где поля нет. Он никогда не проставляет версию, которой на странице не существует, и не перезаписывает уже заполненное значение. |
| Гигиена формулировок | План, п. 5: «Точный расчёт по вашей комплектации» → «Предварительный расчёт…» в блоке модельных страниц. |

Публичный API рантайма дополнен `ASTConversion.sourceParams()` и
`ASTConversion.consentVersion()` — для проверки из консоли на бою.

## Что остаётся вручную

1. **Создать цель `ast_form_start`** в Метрике 106049767 (тип «JS-событие»,
   идентификатор `ast_form_start`) — рядом с целями из
   `docs/tracking-check-2026-09.md`. Без этого событие уходит, но в отчётах
   его не будет.
2. **Проверить отказы** — отчёт «Содержание → Параметры визитов → `ast_source`»,
   разрезы `utm_source_type` и `utm_content`. Это и есть шаг 5 аудита;
   выполнять не раньше чем через 48–72 часа после накопления трафика.

   Пункты 1 и 2 автоматизированы — `scripts/metrika.py` (`create-goals` создаёт
   все цели Этапа 1 включая `ast_form_start`, `bounce` строит отчёт), нужен
   OAuth-токен Метрики в `METRIKA_OAUTH_TOKEN`. Запускать с
   машины, у которой есть сеть до `api-metrika.yandex.net`: в облачном
   окружении Claude Code с политикой «trusted network access» все домены
   Яндекса и `tilda.cc` отдают 403 на CONNECT, поэтому проверить скрипт против
   живого API оттуда нельзя — формы запросов собраны по документации API и
   на боевом счётчике не прогонялись.
3. **Подключить рантайм в Tilda** — «Настройки сайта → Ещё → HTML-код для
   вставки внутрь BODY». На Tilda путь `/assets/...` не существует, поэтому
   ссылкой, как в снапшоте, подключить нельзя — код вставляется инлайном:

   ```
   python3 scripts/build-tilda-snippet.py    # соберёт build/tilda-body-snippet.html
   ```

   Содержимое файла вставляется целиком (~59 КБ: `<style>` с CSS и `<script>`
   с рантаймом). Пересобирать после каждой правки рантайма, иначе боевой сайт
   разойдётся со снапшотом.

   По состоянию на 03.09.2026 пункт «Подключить рантайм в Tilda» всё ещё стоит
   невыполненным в `docs/etap1-measurement-conversion.md`. Если это так, то на
   avtonds.ru не работает **весь** контур Этапа 1 — цели, квиз, липкая панель,
   а не только правки этого PR. Проверяется открытием боевой страницы: в
   консоли `ASTConversion` должен быть определён.
4. **Принять поля в CRM.** В заявку добавились `utm_campaign_id`,
   `utm_group_id`, `utm_source_type`, `utm_position_type`, `utm_device`,
   `utm_retargeting`. Если приёмник со строгой схемой — их нужно завести,
   иначе они будут отброшены.

## Найденные расхождения (не исправлялись)

Обе находки касаются юридически значимых значений и данных, поэтому изменены
не были — решение за владельцем.

1. **`consent_version` на сайте не согласован.** В разметке форм встречаются
   два значения: `privacy-2026-05-12` (131 форма) и `privacy-2026-05-06`
   (4 формы — `/auto-s-nds-dlya-biznesa`, `/auto-v-lizing`,
   `/bezopasnaya-pokupka-avto`, `/raschet-avto-pod-klyuch`). Инлайн-конфиг
   на многих страницах по умолчанию тоже отдаёт `privacy-2026-05-06`.
   План (п. 4.2) требует, чтобы версия текста согласия была зафиксирована
   однозначно. Какая из версий соответствует актуальному тексту на `/privacy`
   — вопрос к владельцу и юристу; проставлять версию догадкой нельзя.
2. **`404.html` не подключает рантайм** (`python3 scripts/inject-ast-conversion.py --check`
   показывает его как единственную страницу без сниппета). Состояние
   существовало до этих правок. Для страницы 404 это, скорее всего, осознанно,
   но переходы на неё из Директа не измеряются.

## Что сюда не входит

План AST Reserve v2 в основном относится к другому проекту — Astro-приложению
`projects/ast-reserve/` (`src/site/config.ts`, `npm run pricing:check`,
`lead-delivery.ts`, ветка `codex/ast-reserve`). В этом репозитории — статический
снапшот avtonds.ru, здесь этого кода нет и быть не должно. Разделы 3, 4, 6 и 7
плана (гейты по месяцам, задачи владельца, кодовая очередь ast-reserve, риски)
исполняются вне этого репозитория.

Правки в самом Яндекс.Директе (автотаргетинг, минус-фразы, тексты, ставки)
кодом не делаются и требуют отдельного подтверждения владельца — это прямо
оговорено в разделе «Security / Risk Review» аудита.

Посадочные страницы менять не потребовалось: `/porsche-import`
(H1 «Porsche под заказ с проверкой до оплаты») и `/bezopasnaya-sdelka`
(H1 «Безопасная сделка через аккредитив Сбербанка») соответствуют обещаниям
объявлений, на которые их перевели 14.05.2026.

## Как проверить

Автотест (Playwright, headless) — воспроизводит заход по реальному URL
объявления `1909924594854344322` из раздела «Applied» аудита:

```
npx --yes http-server -p 8199 -s .        # из корня репозитория
node scripts/verify-direct-tracking.mjs   # 6 проверок, ненулевой код при провале
```

Проверяется: параметры визита содержат все измерения Директа; скрытые поля
формы несут источник и `consent_version`; `ast_form_start` срабатывает и
дедуплицируется; на органике `ast_source` не отправляется; непойманных
JS-ошибок нет.

На бою — открыть посадочную с `?_ym_debug=1`: в консоли видны и `reachGoal`,
и передача параметров визита. Без Метрики то же самое видно в
`window.dataLayer` (событие `ast_source_params`).
